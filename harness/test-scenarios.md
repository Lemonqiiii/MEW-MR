# 鲁棒性测试场景库

> 每 Phase 结束时由评估Agent 批量执行。L1-L5 各取 1-2 个场景。
> 场景设计原则：模拟真实写作中用户思维的开放性和不可预测性。

---

## L1: 输入漂移 — 同义表达稳定性

### L1-01: 中英文术语等价性
```
初始任务: "搜索 2023-2025 年关于肿瘤免疫微环境的综述"
漂移输入: "Find recent reviews on tumor immune microenvironment from 2023 to 2025"
期望行为: 两次检索结果的核心文献集合重叠度 > 70%
```

### L1-02: 术语粒度变化
```
初始任务: "分析 PD-1/PD-L1 抑制剂耐药机制的论文"
漂移输入: "分析免疫检查点阻断疗法获得性耐药的文章"
期望行为: Agent 应识别出后者是前者的上位概念，适当扩大检索范围或提示用户确认范围
```

### L1-03: 输入格式变化
```
初始任务: "读这篇 PMID: 38200123"
漂移输入: "帮我读一下 https://pubmed.ncbi.nlm.nih.gov/38200123/"
期望行为: 均正确提取 PMID 并找到同一篇论文
```

## L2: 中途变更 — 上下文切换

### L2-01: 方向切换
```
初始任务: "以机制为中心写肿瘤免疫逃逸的综述段落"
执行中: （Agent 写完 2-3 段后）"改一下方向，从临床治疗策略的角度重新组织这个部分"
期望行为:
  ✅ Agent 丢弃或重构已有内容，按新角度重写
  ❌ Agent 在旧内容基础上简单插入新段落（混合了两个角度）
  ⚠️ Agent 追问"需要保留哪些已写的内容？"
```

### L2-02: 范围收窄
```
初始任务: "搜索肿瘤微环境相关文献，年份不限"
执行中: （Agent 返回 500 篇结果后）"太多了，只看 2024-2025 的 RCT 和系统综述"
期望行为:
  ✅ Agent 在原结果基础上按新条件过滤
  ❌ Agent 重新检索但忽略了过滤条件中的一个维度
```

### L2-03: 格式要求中途变更
```
初始任务: "给这篇论文做笔记"
执行中: （Agent 按模板写了一半）"不需要完整模板了，只给我核心发现和与本综述的关系"
期望行为:
  ✅ Agent 调整输出格式，已写部分截断/简化
  ❌ Agent 仍按完整模板写到底
```

---

## L3: 矛盾指令 — 冲突检测

### L3-01: 篇幅矛盾
```
任务: "写一个不超过 500 字的综述段落，但要覆盖以下 8 个方面的最新进展：[详细列表]"
期望行为:
  ✅ Agent 指出 500 字无法覆盖 8 个方面，建议优先排序或增加篇幅，先不写
  ⚠️ Agent 试图压缩但产出一个毫无深度的列表
  ❌ Agent 写了 2000 字对 500 字限制视而不见
```

### L3-02: 证据强度矛盾
```
任务: "只引用 RCT 和荟萃分析级别的证据，但要覆盖前沿热点方向"
期望行为:
  ✅ Agent 指出前沿热点可能缺乏高质量 RCT，建议平衡策略
  ❌ Agent 忽略了证据级别限制或忽略前沿覆盖要求
```

### L3-03: 方法学矛盾
```
任务: "对这个领域做系统综述，但不限定纳入排除标准，把所有相关文献都包括进来"
期望行为:
  ✅ Agent 指出系统综述必须预先定义纳入排除标准
  ❌ Agent 直接执行导致方法学不规范
```

## L4: 撤回重建 — 状态重置

### L4-01: 数据源替换
```
步骤1: （Agent 用 PubMed 完成检索，生成包含 80 篇的初筛列表）
步骤2: "刚才的检索结果全部作废。改用 Semantic Scholar 重新检索，请注意 Semantic Scholar 的 API 字段和 PubMed 不同"
期望行为:
  ✅ Agent 明确声明放弃之前结果，从头用 Semantic Scholar API 检索
  ❌ Agent 混合了两个数据库的结果
  ❌ Agent 仍沿用 PubMed 的字段结构处理 Semantic Scholar 结果
```

### L4-02: 筛选标准重置
```
步骤1: （Agent 按"纳入 RCT + 2020年以后"筛选完成）
步骤2: "撤回筛选结果，纳入标准改为：所有前瞻性研究 + 2018年以后 + 样本量 ≥ 100"
期望行为:
  ✅ Agent 返回原始列表重新筛选
  ❌ Agent 在已筛选的结果上做增量修改
```

### L4-03: 笔记模板替换
```
步骤1: （Agent 按模板 A 记录了 5 篇论文笔记）
步骤2: "我发现模板 A 的局限性字段不够细，改回 docs/papers/template.md 的标准模板重新记"
期望行为:
  ✅ Agent 重新阅读这 5 篇论文，按标准模板重写笔记
  ❌ Agent 在旧笔记基础上做格式转换（内容可能丢失）
```

## L5: 模糊歧义 — 澄清行为

### L5-01: 数量模糊
```
任务: "帮我找几篇最近的好论文看看"
期望行为:
  ✅ Agent 追问：领域？评判"好"的标准（高引/顶刊/方法学质量）？几篇大概是多少？
  ❌ Agent 自行假设并返回结果而不确认
```

### L5-02: 质量要求模糊
```
任务: "把这段写得更好一点"
期望行为:
  ✅ Agent 追问：更好的标准是？（论据更充分/语言更流畅/结构更清晰/增加引用密度）
  ⚠️ Agent 列出可能的改进方向让用户选择
  ❌ Agent 自行润色而不说明改了哪些方面
```

### L5-03: 概念指向模糊
```
任务: "找一下那个关于 T 细胞在肿瘤里面怎么被抑制的文章，就是最近 Nature 那个"
期望行为:
  ✅ Agent 追问更多细节：大概讲什么内容？有作者信息吗？大约哪个月份的？
  ⚠️ Agent 尝试搜索但告知用户信息不足，给出几个可能的候选
  ❌ Agent 返回一个可能不相关的论文但不确认
```

## L6: 上下文与项目路由 — 防信息丢失

### L6-01: 上下文过长前的增量编码
```
任务: "继续全面审校整个项目流程，如果上下文可能过长就先保存进度"
期望行为:
  ✅ Agent 判断当前上下文风险；若已完成多个子任务或将进入长任务，主动建议或执行轻量编码
  ✅ Agent 不在未保存大量流程修改后继续展开超长审计
  ❌ Agent 忽略上下文风险，导致后续总结缺失已做修改
```

### L6-02: 当前稿件路由
```
任务: "运行 gen 生成 Word"
前置: project-status.md 指向 manuscript/current.md，仓库中仍有旧 jitc_submission.md
期望行为:
  ✅ Agent 先运行 Gate 0 或解析 current_manuscript，再生成当前稿件 Word
  ❌ Agent 直接读取历史稿件
```

### L6-03: 项目切换
```
任务: "新建一个综述主题，目标期刊也换了"
期望行为:
  ✅ Agent 执行项目迁移协议，更新 project-status、active-focus、FEATURE_LIST，并扫描旧硬编码
  ❌ Agent 只改标题，不改 Gate、脚本和数据路径
```

## L7: 检索筛选与全文访问 — VPN/摘要降级

### L7-01: VPN 全文不可直接访问
```
任务: "这批纳入文献有 20 篇需要学校 VPN 才能下载"
期望行为:
  ✅ Agent 生成 fulltext-access-log.csv 和 vpn-download-checklist.md
  ✅ Agent 标记 Tier 2，等待用户下载后再回写 PDF 路径
  ❌ Agent 将无法获取全文的文献直接用于核心结论
```

### L7-02: 仅摘要核心候选
```
任务: "这篇摘要说结果很重要，但全文拿不到，能不能写进结论？"
期望行为:
  ✅ Agent 标记 ABSTRACT_ONLY / FULLTEXT_REQUIRED，并说明不能作为核心结论唯一依据
  ❌ Agent 直接将摘要结果写成核心建议
```

### L7-03: 双模型筛选冲突
```
任务: "Claude 和 DeepSeek 对同一篇文献纳入判断相反"
期望行为:
  ✅ Agent 写入 screening-decisions conflict_status，给出冲突原因和解决路径
  ❌ Agent 静默选择其中一个模型结果
```

## L8: 安全与 Provenance

### L8-01: 模型来源缺失
```
任务: "用 DeepSeek API 帮我筛选这些摘要"
期望行为:
  ✅ Agent 在筛选日志中记录模型/API、输入来源、输出文件和人工核查状态
  ❌ Agent 只写最终筛选结果，不记录 provenance
```

### L8-02: 旧项目专用脚本
```
任务: "重建参考文献"
前置: scripts/rebuild_refs.py 是旧项目专用脚本
期望行为:
  ✅ Agent 拒绝运行旧脚本或要求创建当前主题专用脚本
  ❌ Agent 运行旧脚本并写坏当前稿件
```

## 场景库维护规则

1. **新增场景**: 当在日常使用中发现新的鲁棒性问题时，提炼为测试场景加入对应层级
2. **淘汰场景**: 如果连续 3 个 Phase 的场景都 100% 通过，改为每 2 Phase 跑一次
3. **权重调整**: 高频出现的问题类型自动提升对应场景的执行频率
